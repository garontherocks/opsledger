# Phase 17 owned n8n Community profile

Pinned runtime: n8n 2.42.6, official release checked 2026-10-09. This is self-hosted Community under the Sustainable Use license, not unrestricted OSI open source. Internal learning is the intended use. Paid hosting, enterprise SSO/RBAC/Git environments and public services are not included. [License](https://docs.n8n.io/sustainable-use-license), [CLI](https://docs.n8n.io/deploy/host-n8n/configure-n8n/use-the-command-line.md), [security variables](https://docs.n8n.io/hosting/configuration/environment-variables/security/).

Use a separate empty owned n8n instance. Do not import over an existing workflow/credential ID. Native npm self-hosting with `n8n@2.42.6` is suitable for the Windows lab; Node 24.19.0 is retained. Bind n8n to 127.0.0.1:5678, disable telemetry/version/templates/community packages, block node environment/file access, exclude Code/ExecuteCommand/SSH/read-write-file nodes, and disable saving success/error/manual execution input. Use private local n8n settings/encryption key. This trusted synthetic profile is not production sandboxing; workflow editors remain privileged. Never expose it by tunnel.

Import `qa-report.json` into this owned instance. Configure the two referenced Header Auth credentials locally: QaInbound uses x-qa-inbound and the private QA_N8N_INBOUND_TOKEN; QaService uses authorization and Bearer QA_SERVICE_TOKEN. Neither value nor the separate QA_WEBHOOK_SIGNING_KEY is in the export. Signature generation belongs to the local operator; n8n receives a signature and cannot mint one. Review the fixed service URL; no model-selected URL/expression or Code node exists. Publish this one workflow through the owned instance UI, not all workflows. The pinned runtime uses publication outbox activation by default. The CLI publish:workflow changes the active version but did not register this webhook in actual CI; CLI success is insufficient evidence of live trigger activation. CI uses the owned synthetic owner session to call the native activate API and verifies publication-status against the imported version and trigger. No publication flag or security policy is disabled.

Use the existing migrated owned OpsLedger lab, existing password and AUTH_SECRET. The operator creates/checks one QA run through the M4 UI, then sets private QA_SERVICE_RUN_ID, QA_SERVICE_WORKSPACE_ID, QA_SERVICE_USER_ID (same owning reviewer), QA_SERVICE_EXPIRES_AT (epoch ms), independent QA_SERVICE_TOKEN and QA_WEBHOOK_SIGNING_KEY, plus exact reviewed QA_TARGET_SHA. Additive migration 0009 is required; do not reseed/reset the existing DB. Run `node --env-file=.env --experimental-strip-types scripts/qa-orchestration-server.ts` on loopback 3101. Credentials permit only inspect and consumption of the existing signed approval for this one run. They cannot create runs, choose suites, approve, or act on incidents.

`node --env-file=.env --experimental-strip-types scripts/qa-webhook.ts inspect` forwards one signed event through n8n. Failed deterministic checks remain failed; disabled/timed-out/malformed triage is inconclusive. A valid draft/abstention is unverified and waits for review; n8n cannot approve. The owning reviewer approves or denies using the existing UI. To consume that specific approval: `node --env-file=.env --experimental-strip-types scripts/qa-webhook.ts store_report <approval-id>`. Expiry/SHA/action/identity remain enforced by M4. A response saying pending/awaiting_review/inconclusive is not a stored report or quality/release pass. A stored report still has qualityVerified=false and releaseAuthority=false.

HTTP retries are bounded to two attempts and use the same signed event ID/body; durable deduplication and one-time approval protect effects. An expired replay window is denied. A failed transport/credential request follows the explicit denied/unavailable branch and does not claim completion. For a new inspect after human review, emit a new event; cached inspection is historical, not live state. Revoke/rotate short-lived service credentials afterwards.

CI `scripts/phase17-n8n.ts` runs the real Docker image on an internal-only bridge, imports temporary synthetic credentials, uses real signed webhooks/native DB/controller, tests duplicates and denial, exports the actual workflow and scans for its temporary secret values. It deletes only resources it created. Triage and approvals are fixtures, not model/human-quality evidence. Docker is unavailable in Work; local bridge tests do not substitute for this required runtime gate. No manual desktop repeat is required before M5's consolidated checkpoint.
